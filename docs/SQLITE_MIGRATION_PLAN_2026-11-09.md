## وضع البيانات والرؤية الأمنية

أكد مالك النظام في 2026-11-09 أن ملفات الحسابات والحوالات والمستخدمين الموجودة حالياً تحتوي على بيانات وهمية وتجريبية فقط، وليست بيانات عملاء أو معاملات مالية حقيقية. بناءً على هذا التأكيد، لا يلزم تحويل المستودع إلى Private لمجرد وجود ملفات JSON التجريبية، والمستودع ما زال Public عند آخر تحقق.

هذا التأكيد لا يعني السماح بنشر أسرار حقيقية. قبل أي إصدار عام يجب التحقق من عدم وجود:
- مفاتيح API أو GitHub tokens أو أسرار JWT حقيقية.
- كلمات مرور أو PINs مستخدمة فعلياً خارج بيئة الاختبار.
- بيانات شخصية حقيقية أضيفت لاحقاً إلى ملفات الاختبار أو السجلات.

يجب إلغاء أي GitHub token سبق نشره وإصدار بديل محدود الصلاحيات. كما يجب أن تبقى بيانات التشغيل المستقبلية خارج Git، حتى لو كانت بيانات اليوم تجريبية.

**حاجز الترحيل:** لا يُحذف أي ملف JSON ولا يُستبدل أثناء بناء SQLite. تُنشأ قاعدة اختبار منفصلة، وتبقى ملفات المصدر كما هي. تُحفظ نسخة احتياطية من مجموعة الاختبار قبل تجارب الاستيراد، ويُتحقق من سلامتها ببصمات SHA-256. هذا الحاجز لحماية سلامة الملفات من الفقد أو التلف، وليس شرطاً لجعل المستودع خاصاً.

يجب على أداة الترحيل أن تصدر تقريراً عن وجود كل ملف وحجمه وعدد السجلات وبصمة SHA-256، لا محتواه الحساس. ويجب أن تتوقف إذا كان هناك ملف مفقود أو تالف أو علامة معاملة مالية معلقة.

## اختيار التقنية

الهدف هو SQLite محلي على جهاز Windows واحد ومستخدم واحد، مع قاعدة بيانات واحدة تكون مصدر الحقيقة.

تم اختيار واجهة SQLite المدمجة في Node.js عبر `node:sqlite` لتجنب إضافة native addon أو تعديل lockfile في هذه المرحلة. يتطلب المشروع Node.js `>=22.13.0`، ويجب التحقق من الإصدار المضمّن فعلياً في أي حزمة Windows/Electron قبل اعتمادها. لا نعتمد على SQLite WASM أو ملف JSON بديل لتخزين الحسابات المالية.

المتطلبات التشغيلية لقاعدة البيانات:
- ملف دائم خارج مجلد البرنامج، داخل مجلد بيانات المستخدم، وليس داخل مجلد التثبيت أو مجلد مؤقت.
- `PRAGMA foreign_keys=ON`.
- `PRAGMA journal_mode=WAL` بعد اختبار سلوك النسخ الاحتياطي والاستعادة على Windows.
- `PRAGMA synchronous=FULL` للعمليات المالية.
- `busy_timeout` مناسب، وقفل يمنع تشغيل نسختين من التطبيق على قاعدة البيانات نفسها.
- ترحيلات مخطط مرقمة في جدول `schema_migrations`، وتنفذ داخل معاملات.
- كل عملية مالية كاملة، بما فيها اليومية وخطوط القيد وتحديث أرصدة الحسابات وسجل التدقيق ومفتاح منع التكرار، يجب أن تحفظ في معاملة SQLite واحدة.
- لا تستخدم `REAL` للمبالغ المالية. تخزن المبالغ كأعداد صحيحة بوحدة نقدية فرعية معلومة لكل عملة، ومعدلات الصرف كقيم scaled integers أو تمثيل عشري نصي مضبوط. يجب أن يحدد التحويل من JSON قواعد التقريب والتحقق قبل التنفيذ.
- لا يوجد dual-write بين JSON وSQLite في الإنتاج؛ بعد التبديل تكون قاعدة واحدة هي المرجع الوحيد.

## نموذج البيانات المستهدف

هذا نموذج منطقي أولي؛ لا يُعتمد نهائياً إلا بعد مطابقة جميع حقول الأنواع الحالية في الكود:

1. `accounts`: دليل الحسابات ومعرفاته وأكوادها وأنواعها.
2. `account_balances`: رصيد كل حساب لكل عملة، مع قيد فريد على (account_id, currency).
3. `journal_entries`: رأس القيد، المرجع، نوع العملية، المستخدم، الوقت، ومفتاح idempotency فريد.
4. `journal_lines`: أطراف القيد، الحساب، العملة، المدين والدائن، مع قيود تمنع وجود مدين ودائن معاً في السطر.
5. `remittances`: سجل الحوالة الرئيسي وحالتها وبيانات المرسل والمستفيد والشبكة.
6. `remittance_number_reservations`: حجز أرقام الحوالات مع قيد UNIQUE.
7. `remittance_payouts`: أحداث الصرف وربطها بالحوالة والقيد.
8. `exchange_rates` و`exchange_rate_audit`: الأسعار المعتمدة وسجل تغييرها.
9. `cashier_shifts` و`cashier_shift_events`: الورديات والفتح والإقفال والجرد والفروقات.
10. `app_users` و`auth_audit`: المستخدمون وتدقيق الدخول؛ تبقى كلمات/PINs السرية في حقول hash/salt فقط.
11. `financial_audit_log`: سجل تدقيق غير قابل للتعديل العادي.
12. `idempotency_records`: مفاتيح الطلبات وبصمات المحتوى ونتائجها لمنع تكرار العمليات.
13. `whatsapp_dispatches` و`notification_events`: حالة الإرسال والأحداث. تبقى الصور/المرفقات ملفات خارجية، ويخزن مسارها وبصمتها وبياناتها الوصفية في SQLite.
14. `app_settings`: إعدادات التشغيل والترقيم غير السرية.

يجب فرض توازن المدين والدائن لكل قيد ولكل عملة داخل الخدمة/المعاملة، وعدم الاعتماد على Trigger وحده للتحقق من إجمالي متعدد الصفوف.

## خطة التنفيذ الآمنة

### المرحلة 0 — حماية مجموعة الاختبار (حاجز إلزامي)
- التعامل مع البيانات الحالية على أنها بيانات تجريبية وفق تأكيد المالك، وعدم إدخال بيانات حقيقية إلى Git.
- مراجعة الأسرار الحقيقية بشكل منفصل؛ لا يشترط جعل المستودع خاصاً بسبب ملفات الاختبار وحدها.
- إنشاء نسخة احتياطية من مجموعة الاختبار قبل أي تجربة استيراد.
- جرد ملفات التشغيل، وحساب SHA-256، والتحقق من عدم وجود `financial_transaction_pending.json`.
- لا يبدأ الترحيل إذا كانت علامة الاسترداد موجودة أو إذا لم تتوازن الدفاتر أو تعذر قراءة ملف.

### المرحلة 1 — طبقة SQLite مستقلة دون تشغيل النظام عليها
- [x] اعتماد `node:sqlite` المدمج في Node.js، مع حد أدنى معلن Node.js `>=22.13.0`.
- [x] إضافة وحدة فتح اتصال مستقلة تضبط foreign keys وWAL وsynchronous=FULL وbusy_timeout.
- [x] إضافة مشغل migrations مرقمة مع SHA-256، ومنع تعديل migration سبق تطبيقها، وتنفيذ كل migration داخل transaction.
- [x] إضافة اختبارات تأسيسية للفتح والإعدادات والعلاقات والـ rollback وإعادة الفتح.
- [ ] تشغيل الاختبارات فعلياً على CI وعلى Windows.
- [ ] إضافة مخطط الأعمال الفعلي بعد مطابقة أنواع البيانات الحالية.
- لم يتم ربط أي خدمة قائمة بـ SQLite، ولم يتم إنشاء قاعدة تشغيلية.

### المرحلة 2 — أداة ترحيل جافة (Dry Run)
- تقرأ ملفات JSON من مجلد البيانات المحلي فقط.
- تتحقق من JSON schema، المعرفات المكررة، العلاقات، العملات، الأرقام، توازن القيود، ومطابقة الأرصدة المحسوبة مع الأرصدة المخزنة.
- تحسب تقرير counts + totals + checksums دون كتابة إلى قاعدة البيانات.
- تحول المبالغ بدقة دون تقريب صامت.
- ترفض الاستمرار عند أي فرق أو بيانات مجهولة.

### المرحلة 3 — استيراد تجريبي إلى قاعدة جديدة
- تنشئ نسخة قاعدة جديدة في مسار مؤقت.
- تنفذ استيراد كل نطاق داخل transaction، مع rollback كامل عند الخطأ.
- تقارن عدد السجلات والأرصدة والقيود والحوالات والورديات والأسعار ومفاتيح منع التكرار.
- تشغل `PRAGMA integrity_check` و`foreign_key_check`.
- لا تحذف ولا تعدل ملفات JSON الأصلية.

### المرحلة 4 — تحويل خدمة واحدة في كل مرة
الترتيب المقترح:
1. دليل الحسابات والأرصدة واليومية معاً.
2. الحوالات وأرقامها وعمليات صرفها.
3. الصرافة وأسعار الصرف.
4. الورديات.
5. المستخدمون وسجل المصادقة.
6. الإرسال وسجلات الإشعارات، مع إبقاء الصور في الملفات.

كل خدمة لها اختبارات وحدة وHTTP وتزامن وإعادة تشغيل مستقلة. لا يتم تشغيل وضع إنتاج مختلط بين JSON وSQLite.

### المرحلة 5 — اختبار Windows والاستعادة
- اختبار تثبيت/تشغيل على Windows نظيف دون إنترنت.
- اختبار إيقاف قسري للعملية في مراحل متعددة من المعاملة.
- إعادة تشغيل النظام والتحقق من عدم وجود قيد نصف مكتمل.
- التحقق من WAL وcheckpoint وملفات sidecar.
- نسخ احتياطي واستعادة إلى مسار مختلف، ثم مطابقة الأرصدة وعدد القيود.
- تجربة استعادة فعلية قبل أي اعتماد.

### المرحلة 6 — التبديل والإصدار
- نسخة احتياطية نهائية قبل التبديل.
- تشغيل قاعدة SQLite وحدها بعد اعتماد جميع المقارنات.
- الاحتفاظ بملفات JSON الأصلية كأرشيف للقراءة فقط خارج مسار التشغيل، وعدم حذفها حتى موافقة المالك بعد نجاح فترة تحقق.
- تجهيز EXE فقط بعد اجتياز اختبارات Windows والاستعادة.

## شروط القبول قبل اعتماد SQLite

- لا يوجد فرق في إجمالي الأرصدة لكل حساب وعملة بين المصدر والوجهة.
- كل قيد متوازن لكل عملة، ولا توجد قيود يتيمة أو مكررة.
- أرقام الحوالات فريدة، وحالة كل حوالة متوافقة مع سجل الصرف والقيد.
- كل مفتاح idempotency فريد، وإعادة الطلب لا تنشئ أثراً مالياً ثانياً.
- لا توجد معاملة مالية معلقة قبل الترحيل.
- فشل أي خطوة داخل المعاملة يعيد كل التغييرات (rollback).
- إعادة التشغيل بعد kill/crash لا تترك حالة جزئية.
- النسخ الاحتياطي والاستعادة يعيدان قاعدة قابلة للفتح ومتطابقة.
- نجاح الاختبارات على Windows الفعلي، وليس Linux CI فقط.
- لا يحتوي Git على بيانات تشغيلية أو أسرار.

## ما لم يتم في هذه المرحلة

- لم تتم إضافة dependency خارجية؛ استُخدم `node:sqlite` المدمج في Node.js.
- لم يتم إنشاء ملف قاعدة بيانات تشغيلية؛ الاختبارات فقط تنشئ قواعد مؤقتة عند تشغيلها.
- لم يتم ربط الخدمات أو endpoints الحالية بـ SQLite.
- لم يتم تنفيذ ترحيل بيانات JSON أو تغيير ملفاتها.
- لم يتم تعديل رؤية المستودع.
- لم يتم تعديل `main` أو دمج PR #2.
- لم يتم تأكيد نجاح اختبارات SQLite بعد؛ يلزم انتظار CI واختبار Windows.

**قرار المراجعة:** لا تبدأ كتابة محرك SQLite أو نقل بيانات حقيقية قبل إغلاق حاجز حماية المستودع العام والنسخ الاحتياطي. هذه ليست خطوة شكلية؛ هي شرط لحماية بيانات العملاء والمستخدمين ومنع فقد الأرصدة.
