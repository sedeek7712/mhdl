# تدقيق مطابقة مخطط SQLite مع نماذج التشغيل

**التاريخ:** 9 نوفمبر 2026  
**المستودع:** `sedeek7712/mhdl`  
**الفرع المرجعي:** `storage/windows-preflight-2026-11-09`  
**Commit المراجع:** `36e826bd10886385f704d240b5e0a1f2f5f7ad2b`  
**نوع الفحص:** قراءة ساكنة ومقارنة نماذج TypeScript بخريطة SQLite؛ لا يتضمن ترحيلاً أو تشغيل خدمات مالية على SQLite.

## 1. القرار التنفيذي

مخطط SQLite v1 أساس جيد لدفتر الحسابات والحوالات، لكنه **غير مكتمل لترحيل النظام كله**. وجود جدول في DDL لا يعني أن بيانات ملف JSON المقابل تُستورد أو أن دورة الخدمة صارت تعمل على SQLite.

يبقى JSON مصدر التشغيل الحالي. لا يجوز تحويل أي خدمة مالية قبل إكمال المطابقة والاختبارات والاستعادة.

## 2. ما يغطيه الإصدار الأول

تتضمن Migration v1 خمسة عشر جدولاً في المجالات التالية:

- دليل الحسابات وأرصدة العملات.
- رؤوس القيود وخطوطها ومفاتيح منع التكرار.
- إعدادات ترقيم الحوالات والحجوزات وسجلات الحوالات والصرف وتدقيق الحوالات.
- أسعار الصرف وسجل تغييراتها.
- الورديات وأرصدة الوردية وأحداثها.

أداة Dry Run الحالية تستورد الحسابات والقيود وإعدادات الحوالات والحجوزات والحوالات وسجلات الصرف وتدقيق الحوالات. نجاح الاختبار على هذه المجموعة لا يثبت استيراد أسعار الصرف أو الورديات أو المستخدمين أو WhatsApp.

## 4. ملاحظات فنية مهمة

### 4.1 بصمات الوردية

خدمة الورديات الحالية تحفظ مفتاحي الفتح والإقفال وبصمة طلب كل منهما. البصمتان تميزان إعادة الطلب الآمنة عن إعادة استخدام المفتاح لطلب مختلف. مخطط v1 يحتوي المفتاحين لكنه لا يحتوي عمودي البصمة. لا يجوز حذف هذه البصمات عند الانتقال.

### 4.2 توازن القيود

المستودع الحالي يفحص توازن كل عملة قبل إدخال القيد ويكتب رأس القيد وخطوطه وتحديث الأرصدة داخل معاملة واحدة. أما شرط `is_balanced = 1` في رأس القيد فلا يثبت وحده أن مجموع خطوط المدين يساوي مجموع الدائن. يجب أن تكون الكتابة محصورة في مستودع مالي موثوق، مع اختبارات تمنع أي مسار إدخال مباشر يتجاوز الفحص.

### 4.3 العلاقة بين الحوالة والصرف

جدول الصرف مربوط برقم الحوالة الموحّد، لكن `transfer_id` غير مربوط بمفتاح الحوالة الأساسي. قبل الاعتماد يجب التحقق أن المعرف والرقم يعودان إلى السجل نفسه، وأن مبلغ الصرف وعملته وحالته ورقم القيد متطابقة. لا يكفي وجود Foreign Key على رقم الحوالة فقط.

### 4.4 مجلد بيانات Windows

المخازن JSON الحالية تعتمد مساراً مشتقاً من مجلد مصدر الخادم، بينما SQLite يستخدم `LOCALAPPDATA`. عند التعبئة إلى EXE لا يجوز افتراض أن مجلد المصدر قابل للكتابة. يجب توحيد كل الخدمات على مسار بيانات المستخدم، مع تهيئة المجلد والأذونات والنسخ الاحتياطي قبل تشغيل الخادم.

### 4.5 SQLite وواجهة Node

اختبار Node 24 على Windows يثبت أن اختبارات الأساس تعمل في بيئة Windows CI، لكنه لا يثبت توافق Electron أو بناء EXE أو سلوك إطفاء التطبيق. كما أن استخدام `node:sqlite` يحتاج مراجعة مستوى استقراره في إصدار Node المضمّن فعلياً داخل Electron قبل اعتماده تشغيلياً.

## 5. ترتيب التنفيذ المقترح

1. **Migration v2 للورديات وأسعار الصرف:** إضافة حقول بصمات فتح/إقفال الوردية، ثم استيراد أسعار الصرف والورديات مع مقارنة حقلية واختبارات replay.
2. **Migration للمستخدمين والمصادقة:** نقل بيانات المستخدمين بصورة آمنة مع إبقاء سر JWT خارج SQLite، واختبار استمرار الجلسة وإبطالها بعد إعادة التشغيل.
3. **Migration لـ WhatsApp والمرفقات:** استيراد سجل المحاولات والحالات والأحداث والـ snapshots، والتحقق من أن كل صورة أرشيفية موجودة وبصمتها صحيحة.
4. **تقوية العلاقات المالية:** علاقة payout بالمعرف والرقم معاً، والتحقق الكامل من حوالة/صرف/قيد، ومنع الكتابة خارج المستودع.
5. **طبقة مسارات بيانات Windows:** مسار موحد داخل مجلد بيانات المستخدم، قفل نسخة واحدة، وإغلاق منظم لاتصال SQLite.
6. **النسخ والاستعادة:** نسخة احتياطية متسقة مع WAL واختبار استعادة فعلي قبل أي تبديل.
7. **Electron وEXE:** إنشاء نقطة تشغيل Electron بعد حسم إصدار Node المضمّن، ثم اختبار تثبيت نظيف وتشغيل دون إنترنت وإطفاء قسري وإعادة فتح.

## 6. شروط عدم البدء بالترحيل الحقيقي

يظل الترحيل الحقيقي ممنوعاً حتى تتحقق كل الشروط التالية:

- وجود نسخة خط أساس افتتاحي معتمدة ومطابقة مع الأرصدة الحالية وحركة اليومية.
- عدم وجود `financial_transaction_pending.json` أو أي معاملة مالية معلقة.
- تطابق جميع السجلات والأرصدة لكل حساب وعملة، والحوالات مع سجلات الصرف والقيود.
- استيراد أسعار الصرف والورديات والمستخدمين وWhatsApp والمرفقات أو توثيق استثناء معتمد لكل نطاق.
- نجاح اختبارات التزامن ومنع التكرار والـ rollback وإعادة التشغيل.
- نجاح Windows/Electron واختبارات النسخ الاحتياطي والاستعادة.
- عدم حذف ملفات JSON الأصلية حتى نجاح المقارنة واعتماد المالك.

**الخلاصة:** SQLite v1 أساس تجريبي ناجح، وليس بديلاً مكتملاً عن مخازن JSON الحالية. الخطوة التالية الصحيحة هي استكمال المطابقة والاستيراد الجاف لكل نطاق، لا تحويل الخدمات المالية الآن.
